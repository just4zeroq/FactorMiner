## 第 2 章 数据、面板与时间语义

> 本章回答：为什么同一个因子、同一份代码、同一段行情，换一种标签写法或换一种时间对齐方式，结论可以完全相反？数据层不是"把 CSV 读进来"这么简单，它决定了整个研究里唯一不可修复的东西——信息是否在未来才可得。前视偏差一旦进入因子值，后面所有统计闸门都只会更精致地验证一个错误答案。

### 2.1 面板：因子研究的基本数据结构

因子研究的输入不是一张表，而是一个**三维张量的稀疏版本**：

```
X ∈ R^{T × N × D}      时间 T × 资产 N × 字段 D
R ∈ R^{T × N}          前瞻收益（标签）
F ∈ R^{T × N}          因子值（或单标的时退化为 R^T）
```

工程上通常有两种布局：

- **长表（long）**：每行 `(date, asset, field...)`，适合增量写入、多源合并、缺失值显式存在；
- **宽表（wide / panel）**：`DataFrame(index=date, columns=asset)`，每个字段一张，适合截面算子 `axis=1` 与 `corrwith(axis=1)`。

FactorMiner 的 `RealDataClient` 在 `cross_asset` 模式下走的是「长表 → 去重 → pivot → reindex」：每个交易对只保留 `required_streams` + 加密流 + `returns`，加 `asset` 列后 concat，按 `['date','asset']` 去重 `keep="last"`，再 `pivot(index='date', columns='asset')`，最后 `reindex(index=all_dates, columns=all_assets)`（`core/data_feed/real_client.py:53-127`）。最后那个 `reindex` 是关键：**缺失格保留 NaN，不丢行**。若某个标的当天没有数据，正确的行为是让它在截面上缺席，而不是把整行删掉或把别的时间对齐过来。

`close` 覆盖率低于 0.90 的资产会触发告警（`:116-123`）。这是一个实践阈值，不是数学真理——它防的是「一个只覆盖 30% 时间的标的，因为恰好在那 30% 里表现好而拉高整体 IC」。

> **原理**：为什么缺失要保留为 NaN 而不是填 0？因为 0 在截面秩里是一个**真实的分位**，会被当成「中等偏下」的打分参与排序；而 NaN 表示「没有观点」。把「不知道」编码成「中性」，是数据层最常见的隐性错误之一。

### 2.2 四个时点：判断前视的唯一标尺

`skills/factorminer-research-architect/references/research-protocol.md` §2 给了一套极简但足够用的时间语义，本书建议把它当成代码审查清单：

| 时点 | 含义 | 约束 |
| --- | --- | --- |
| `feature_end` | 特征所用数据的最晚时点 | 滚动窗口只能用到这里 |
| `decision_time` | 信号形成时点 | 必须 ≥ `feature_end` 所在 bar 的收盘 |
| `entry_time` | 最早允许成交的时点 | 必须 > `decision_time`，通常下一根 open |
| `label_end` | 未来收益计算终点 | `entry_time + h` 根 bar |

四条硬规则：

1. 若使用第 `t` 根 K 线的 `close / high / volume`，默认只能在**该 K 线结束后**知道；
2. 没有更细粒度的成交假设时，不得同时用 `close[t]` 形成信号并假设以同一 `close[t]` 无摩擦成交；
3. forward return 应显式写成 `close[t+h] / entry_price[t+1] − 1` 之类的可核对形式；
4. 发布延迟、交易所时间戳、时区、数据修订都必须进入时间可用性判断。

第 2 条最常被违反。回测里如果用 `close[t]` 的因子值在 `close[t]` 成交，等于假设你能在本根 K 线收盘的同一个瞬间既知道收盘价又能以收盘价成交。FactorMiner 的事件驱动回测用 `ExecutionMode.NEXT_BAR` + `ExecutionPrice.CLOSE`、`next_bar_execution_price=CLOSE`（`core/backtest/backtest_engine.py:417-439`），即信号在第 `t` 根形成、第 `t+1` 根以收盘成交。AlphaMaster 更保守一步：`REBALANCE_ON_BAR_CLOSE=True` / `EXECUTION_LAG_BARS=1`，成交在下一根 open，标签写成 `target_ret[t] = log(open[t+2]/open[t+1])`（`alphamaster_competitor_review.md` §2.5）。

一个容易被忽略的产品级契约是 **`drop_forming=True`**：AlphaMaster 在数据源基类里强制丢弃未收盘 K 线，贯穿 MT5 / TradingView / OKX / A 股 / 通达信 / 国内期货六类数据源（`web/data_sources/base.py:55-60`）。这从根上消除了「回测用了未收盘 bar、实盘看不到」的口径分裂。FactorMiner 的对应做法是增量补数时**裁剪晚于截止日的未收盘 K 线**——一次 2025-01 的补数实测裁掉 652 根越界数据（README §数据更新与新鲜度）。

### 2.3 标签：前瞻收益的精确定义

标签不是 `pct_change()` 一句带过就完事。`core/evaluation/targets.py:16-121` 用一个 frozen dataclass 把它固定下来：

```python
@dataclass(frozen=True)
class ForwardReturnTarget:
    type:         str = "forward_return"
    entry_price:  str = "current_close"   # 或 "next_open"
    exit_price:   str = "close"           # 当前仅支持 close
    horizon_bars: int = 1
    return_type:  str = "simple"          # 或 "log"
```

对应的数学定义（`definition()` 与 `build()`）：

```
current_close 入场 :  r_{t} = close[t+h] / close[t] − 1
next_open    入场 :  r_{t} = close[t+h] / open[t+1] − 1
log 口径           :  r_{t} = log( close[t+h] / entry[t] )
```

实现里 `exit_values = close.shift(-horizon_bars)`，`entry = close` 或 `open.shift(-1)`，`ratio = exit / entry.replace(0, nan)`，最后把 `±inf → NaN`。校验会拒绝 `entry_price` 不在白名单、`horizon_bars` 非正整数（连 `bool` 都拒，因为 Python 里 `True` 是 `int` 的子类）、`return_type` 不是 `simple/log`、以及任何未知字段。

这里有三个容易踩的点：

**其一，标签必须在每个时间切片内独立构造。** `_load_periods_for_pair` 是「逐 period 切片后」才调用 `target_spec.build(sliced_df)`（`real_client.py:135-224`），窗口末尾 `h` 根 bar 自然为 NaN，不会跨越不连续区间去借未来的价格。若先在全样本算好标签再切 `mine_period / test_period`，验证段开头的标签就会用到训练段末尾之后的价格——边界泄漏。

**其二，重叠标签降低有效样本量。** 当 `h > 1` 时，`r_t` 与 `r_{t+1}` 共享 `h−1` 根 bar 的价格路径，IC 序列存在 `h−1` 阶自相关。朴素 `t = mean/(std/√n)` 会把 `n` 当成独立观测数，从而系统性高估显著性。这正是第 13 章要用 Newey–West HAC 的原因；也是 purge 宽度应取 `horizon_bars` 的原因（第 14 章）。

**其三，`h` 决定成本能否被覆盖。** 项目 P0.5 的结论值得原样记住：**1 日目标 + 20 币的年化换手成本 6–17%，大于可得边际，因此必须在交易周期上挖**（`user_workspace/reports/p0_5_return_gate.md`）。标签周期不是随便选的超参，它和换手成本耦合，直接决定策略有没有可能存在。

### 2.4 数据质量：脏数据如何变成"显著因子"

`core/data_feed/panel_validator.py:23-30` 的默认配置：

| 配置 | 默认 | 检查内容 |
| --- | --- | --- |
| `min_coverage` | 0.90 | 面板覆盖率下限（warning） |
| `max_duplicate_ratio` | 0.0 | 重复时间戳（超阈值 → critical） |
| `max_abs_return` | 1.0 | 单期收益绝对值上限，超过视为脏数据 |
| `max_gap_ratio` | 0.05 | K 线缺口比例（warning） |
| `strict` | false | critical 时是否直接拒跑（→ `DataQualityError`） |

`validate_panel` 检查：非 DatetimeIndex、空面板、重复时间戳、索引非单调升序、相邻 bar 间隔与预期不符、覆盖率不足、全 NaN 列 / 常数列、收益全空、极端收益。`RealDataClient._ensure_quality_checked()` 惰性执行一次（`:269-299`）。

这不是洁癖。项目里有过一个真实事故：**31 根重复 K 线混进了 holdout**，而当时没有前置校验，导致严格样本外的结论建立在错误面板上。TODO 里明确写着「正是这条能挡住当初混进 holdout 的 31 根重复 K 线」。真实 20 币面板实测通过时为 366 bars / 0 重复 / 0 缺口 / 覆盖率 100%；正式端到端 run 为 641 bars / 0 warning。

另一类脏数据是「能读但读不出时间」的文件。FactorMiner 的新鲜度扫描会把**读不出时间列或文件名不规范的文件单独报 `unreadable`**，而不是静默跳过——一条 30 MB 没有时间轴的 1m 文件曾因此完全隐形（`core/data_feed/freshness.py`，README §数据更新与新鲜度）。「静默跳过」和「明确报错」的差别，在无人值守的调度里就是「以为数据齐全」和「知道缺了什么」的差别。

### 2.5 加密市场的四个特殊口径

股票框架迁移到加密资产时，最容易出问题的不是代码，是**数据契约**。`docs/research/framework_maturity_crypto_fit.md` 的结论是：把 qlib 或 RD-Agent 改造成加密框架的成本，主要不在代码，而在交易日历、7×24、funding、PIT 资产池和统计口径——恰恰是它们最硬编码的部分。

**（1）7×24 年化口径。** 年化因子 `A` 决定 Sharpe / IR 的展示值：

```
A(1d)  = 365        （不是 252）
A(4h)  = 6 × 365   = 2190
A(1h)  = 24 × 365  = 8760
A(5m)  = 288 × 365 = 105120
sharpe_annual = (mean / std) × √A
```

`core/evaluation/annualisation.py:41-43` 用 `MINUTES_PER_YEAR = 365×24×60 = 525600` 除以 `timeframe` 对应分钟数得到它，解析优先级为：显式 `fitness.annualisation` → `evaluation(.gates).annualisation` → `data_feeds.timeframe` → DatetimeIndex 中位间隔 → 365。1d 数据下 252→365 会让年化 Sharpe 展示值 **`×√(365/252) ≈ 1.203`**（历史报告里的「年化 2.35」在 7×24 口径下应为 2.83）。

这里有一个重要的**口径收窄**，写书时不可夸大：`tests/test_annualisation.py` 锁定「HAC t / p / DSR / promotion gates 在 252↔365↔8760 下逐位相同，只有 `ls_sharpe` 变化」。因为 DSR 判定用的是**每期**净 Sharpe 与 `1/√(n_obs−1)` 尺度的基准，BH-FDR 与 NW-HAC t 根本不消费年化值。所以这是「报告数字正确性」问题，**不是「证伪闸门正确性」问题**——不能用「252 会改变因子通过/拒绝结论」来吓人，但必须修，否则研究者会按错误的数字判断策略强度。行业反例是 `AlphaForge-Crypto`：`backtest.py:163` 用 `√252`，同仓 `bootstrap.py:17` 用 365，自相矛盾。

**（2）加密原生数据流。** funding rate（8h 结算）、open interest、basis、清算流是股票没有的 alpha 来源。`core/data_feed/crypto_streams.py:47-65` 定义 5 条流，其中 `long/short_liquidations` 无免费公开端点，只提供用户自备 feather 的接口。存储路径 `data/<exchange>/<trade_type>/crypto_streams/<safe_symbol>-<tf>-<stream>.feather`。

最核心的一行是 `align_series_to_index()`（`:522-529`）：

```python
return s.reindex(index, method="ffill")   # 只前向填充，绝不 backfill
```

**过去式前向对齐**：一个在 08:00 才公布的 funding 值，只能被 08:00 及之后的 bar 看到，不能回填到 00:00–08:00。模块 docstring 明确写了这是防未来信息泄漏。竞品 `crypto-factor-lab` 用 `funding.shift(1)` 达到同一目的。真实数据现状也值得如实写出：20 个 1d 标的各 funding ≈4240 行、basis ≈1413 行，但 **20 个 `open_interest` 流各仅 25 行**（币安 30 天上限），所以 OI 类特征模板目前基本空跑——「60 个流在盘上」不等于「60 个流可用」。

**（3）Point-in-time 资产池。** 固定 20 币、用「当期非空 + `min_assets`」近似，会带来幸存者偏差：能活到今天的币在历史上天然表现更好，IC 与回测同时虚高。严格做法是上市/退市时间表。这是项目明确列为未完成的一项（`TODO.md` §2b）。

**（4）成本结构。** 永续合约的 funding 是持仓成本而非交易成本，且按 8h 结算、按 bar 频率聚合。`core/backtest/backtest_engine.py:346-414` 的 `load_funding_series()` 用 `series.resample(freq).sum(min_count=1).dropna()`，缺失 bar 保持 NaN 以便 `build_funding()` 回落配置常数（默认 0.0001），并在 `attrs["funding_source"]` 记录是 `"crypto_streams (N assets)"` 还是 `"constant"`。正式 run 里真实 funding 命中 20 个标的。早期版本这里只是 `grid["rate"] = rate` 的常数网格，与 fitness 侧的 18bp 往返成本不同源——两处成本口径不统一是第 15 章的重点。

### 2.6 算法与伪代码：加载一份不会骗自己的面板

```python
def load_panel(config):
    spec = target_from_config(config)            # entry / exit / horizon / return_type
    frames = []
    for pair in config["data_feeds"]["pairs"]:
        raw = read_feather(naming(pair, tf, trade_type))
        raw = drop_dirty_columns(raw)            # 'level_0' / 'index' 等
        raw.index = to_naive_utc_datetime(raw)   # date / time / timestamp(ms) 统一

        # 关键：先切片，再在每个切片内构造标签
        for period in (mine_period, test_period):
            sl = raw.loc[period.start : period.end].copy()
            sl["returns"] = spec.build(sl)       # 末尾 h 根自然 NaN，不跨区间借价格
            frames.append(sl.assign(asset=pair))

    long = pd.concat(frames).drop_duplicates(["date", "asset"], keep="last")
    panel = long.pivot(index="date", columns="asset")
    panel = panel.reindex(index=all_dates, columns=all_assets)   # 缺失保留 NaN

    validate_panel(panel, config["data_quality"])  # 重复/乱序/缺口/覆盖/极端收益
    panel = attach_crypto_streams(panel)           # reindex(method="ffill")，禁 backfill
    return panel[features], panel["returns"], spec  # 特征与标签严格分离
```

这段伪代码里最贵的三行是「先切片再构造标签」「reindex 保留 NaN」「ffill 禁 backfill」。它们都不产生任何炫目的指标，却决定了后面所有数字有没有意义。

### 2.7 竞品对照：数据层契约横向比较

| 框架 | 时间可用性契约 | 年化口径 | 加密原生字段 | PIT 资产池 | 数据质量前置校验 |
| --- | --- | --- | --- | --- | --- |
| qlib | `P/PRef` PIT 算子、`Ref($close,-2)/Ref($close,-1)-1` | 股票 252 | ❌ crypto 采集器只有日频价格/量/市值、无 OHLC | ❌ | ❌ |
| alphalens | 按 date 分组、`max_loss=0.35` | 股票口径 | ❌ | ⚠️ `filter_zscore` 自带前视警告 | ❌ |
| RD-Agent | `RobustZScoreNorm` 用 `fit_start/end_time` 锁定 train | 股票 252 | ❌ CSI300 硬编码 | ❌ | ❌ |
| AlphaMaster | **`drop_forming=True` 全源强制**，三端共用信号函数 | 数据驱动 `ppy` | ❌ 外汇/贵金属为主 | ❌ | ⚠️ 时间轴交集对齐 |
| crypto-factor-lab | `position = desired.shift(1)`，funding `shift(1)` | **24×365 = 8760** | ✅ funding | ⚠️ 仅 BTC 单品种 | ✅ purge 隔离 |
| alpha-factor-mining-crypto | `position` 下一根 | 365d/Δt 数据驱动 | ✅ funding | ❌ 快照选币幸存者偏差 | ❌ |
| **FactorMiner** | 逐切片构标签、`NEXT_BAR/CLOSE`、增量补数裁剪未收盘 bar | 365 / 2190 / 8760 / 105120 | ✅ funding / basis / OI / 清算（部分可用） | ❌ 当期非空 + min_assets 近似 | ✅ `panel_validator` + `freshness` |

一个值得单独记住的判断：`crypto-factor-lab` 是 21 个框架里成熟度 × 加密适配度唯一进入右上象限的另一家（M=8, C=8），但只有 BTC 单品种；FactorMiner（M=9, C=7）是综合可用第一。**「最成熟」与「最适合加密」几乎不重合、接近负相关**：M≥8 的 5 家里 4 家硬编码股票资产池，C≥6 的 3 家里 2 家 M≤6（`framework_maturity_crypto_fit.md` §0.2 / §4.2）。

### 2.8 工程陷阱

1. **`shift(-n)` 用在特征侧**。它只应出现在标签构造里。代码审查时应对每一处 `shift(-` 追问用途。
2. **全样本 `fit_transform`**。标准化参数、分位阈值、缺失值填充统计量只能在训练期拟合，再应用到验证/测试。`walk_forward.py` 的 `_standardise` 明确只在 TRAIN 上取 mean/std（第 13、16 章）。
3. **向后填充（bfill）**。任何把未来值传到过去的 merge / fill 都是直接泄漏；加密流必须 `method="ffill"`。
4. **`center=True` 的滚动窗口**、resample 后把未完成的高周期 bar 提前可用、merge 时未用 as-of 语义。
5. **信号与收益使用同一 bar 的不可成交价格**，以及过滤条件引用了未来完整区间（例如「只保留全样本波动率最低的 20 个币」）。
6. **年化口径与窗口长度混淆**。`portfolio_eval.py:191` 的 `lookback=252` 是滚动**窗口长度**，不是年化因子，不需要跟着改成 365；把它一起改掉是常见的过度修正。
7. **「文件在盘上」当成「数据可用」**。OI 流 25 行、读不出时间列的 30 MB 1m 文件、滞后两个月却没被按周期拆分的 15m 文件，都属于这一类。

### 本章小结

1. 面板的正确布局是 `T × N × D` 的稀疏版本；缺失要保留为 NaN，绝不能填 0——0 是一个真实分位，NaN 才是「没有观点」。
2. 用 `feature_end / decision_time / entry_time / label_end` 四个时点逐条审查，是判断前视偏差唯一可靠的标尺；信号与成交不得落在同一根 bar 的同一价格上。
3. 标签必须**逐时间切片内独立构造**，否则验证段开头会借到训练段之后的价格；`horizon_bars > 1` 带来重叠标签，既要求 HAC 稳健标准误，也要求 purge 宽度 ≥ `h`。
4. 标签周期与换手成本耦合。1 日目标 + 20 币的年化换手成本 6–17% 大于可得边际，这个结论比任何算子调优都更能决定策略存亡。
5. 加密市场的四个特殊口径是：7×24 年化（1d→365、1h→8760）、过去式 ffill 的原生流、PIT 资产池、真实 funding 成本。252 年化只影响展示值，不改变闸门判定——这个收窄必须记准。
6. 数据质量闸门不是洁癖：31 根重复 K 线曾混进 holdout，而「静默跳过」会让 30 MB 的无时间轴文件完全隐形。**能读 ≠ 可用，可用 ≠ 干净**。
