## 第 9 章 大语言模型：从假设到代码与反思闭环

> 本章回答：LLM 在因子研究里究竟站在哪个位置，为什么「调用过一次大模型」不等于「LLM 挖出了因子」；一条生成—执行—反馈闭环如何在没有任何梯度更新的前提下持续演进；提示词、留出纪律与沙盒分别守住哪一道泄漏与安全边界；以及在十余个开源框架之间，FactorMiner 的实现究竟落在哪一层、又有哪些陷阱会让整条链路悄悄失效。

### 8.1 三种位置：先把「用了 LLM」的边界划清

大语言模型进入因子研究，有三类互不等价的位置，混淆它们会直接导致架构选型与竞品判断出错。

第一类是**候选代码生成器**，也就是真正的挖掘范式。LLM 直接吐出可执行的因子代码，代码经过沙盒变成可计算、可评分、可去重、可入库的候选表达式；它占据的是闭环里「生成」这一环，其输出质量由下游 fitness 与闸门裁决。第二类是**假设与实验设计者**：LLM 产出研究假设、因子规格或实验设计，实现与验证交给确定性模块或研究员。微软 RD-Agent 的「假设 → 结构化因子规格 → 代码」两段式调用是这一类的工业级形态，LLM 在这里是研究助手而非搜索算子。第三类是**结果解说员**：模型只读训练快照、指标曲线和公式列表，生成人类可读的分析报告，完全不参与候选生成。

AlphaMaster 是第三类的典型案例，也是最容易被误读的一个。全仓 `/chat/completions` 调用只有两处（`web/ai_providers.py:367`、`web/ai_fallback.py:108`），`model_core/` 与 `train_file.py` 没有任何 LLM 调用；`web/ai_analyze.py:18-66` 的提示是「基于训练快照用中文给出分析」，`build_training_snapshot` 只读进度、公式与曲线（`:148-194`），结果写进 `ai_analysis_history.json` 再以 SSE 回显（`:303-335`）。它的搜索本体是 REINFORCE 加自回归 Transformer，不是 LLM。把解说按钮当成挖掘能力，会凭空多算一个「LLM 挖因子」竞品；更值得警惕的是，这个解说器的 system prompt 明写「不要轻易下『过拟合』结论」「不要因训练分远高于验证分就建议停止」（`web/ai_analyze.py:31,57`）——解说层不但可能被误认，还可能主动稀释统计结论。FactorMiner 的选择是：把解说留给人，把生成留给沙盒，把证伪留给闸门。

FactorMiner 自身的 LLM 范式属于第一类，但必须诚实标注其深度：`docs/research/optimization_plan.md:51` 把它定性为「仅数据感知，不是 RD-Agent 闭环」——它让提示词知道面板里真实有哪些列、这些列的加密语义是什么，却没有假设生成、没有结构化规格、没有独立 critic、也没有单轮内的执行自纠错。调研报告 §3.1.6 的对照表把这一差距列得更直白：FactorMiner 是「同一 system prompt 重复 `batch_size` 次 → 近乎重复候选」，RD-Agent 是「一次假设 → 一次生成 1–5 个具名结构化规格」。承认这一点，才能判断后面每一处工程加固究竟补的是哪个洞。

### 8.2 生成—执行—反馈闭环：无梯度更新的原理与推导

闭环由六步串成：prompt 构造 → 代码抽取 → 沙盒执行 → 指标计算 → 反思记忆 → 下一轮 few-shot。用符号把它写清楚，才能看出「学习」发生在哪里。

设第 t 轮的上下文为

```
C_t = [ S ; F_t ]
```

其中 `S` 是系统提示（角色设定、数据契约、可用字段与变换偏好），`F_t` 是 few-shot 片段，由最近 5 条成功样本 `E⁺` 与最近 5 条失败样本 `E⁻` 拼成。模型参数为 `θ`，采样温度固定，则

```
a_t   = LLM(C_t ; θ)                 # θ 全程冻结，不参与更新
c_t   = clean(a_t)                   # 抽取 ``` 代码块内的纯 Python 源码
v_t   = Sandbox(c_t ; D)             # D 为面板；返回索引对齐的 Series / DataFrame
m_t   = (IC, RankIC, Turnover, fitness)(v_t ; y)   # y 为前瞻收益标签
R_{t+1} = trim_100( R_t ⊕ (c_t, m_t, status) )     # 成功池与失败池各留 100 条
F_{t+1} = last5(R⁺_{t+1}) ⊕ last5(R⁻_{t+1})
C_{t+1} = [ S ; F_{t+1} ]
```

符号解释：`a_t` 是模型原始回答，`c_t` 是清洗后的候选代码，`v_t` 是因子面值，`m_t` 是评估指标，`R_t` 是反思记忆，`y` 是前瞻收益，`⊕` 表示按成功/失败分流追加，`trim_100` 与 `last5` 分别是有界裁剪与最近邻取样。

关键在于 `θ` 从头到尾不变，也就是 `∂L/∂θ = 0`。所谓「无梯度更新」，更新的对象是 `C_t` 而非 `θ`——状态转移 `C_t → C_{t+1}` 完全由记忆的裁剪与选择策略决定，没有任何优化器保证收敛，也没有目标函数保证单调改进。这与第 10 章的神经网络形成根本对照：后者更新的是参数，靠损失函数与反向传播提供方向；前者更新的是上下文，靠文本反馈提供方向，带宽极窄且带噪声。因此闭环的上限不取决于模型规模，而取决于三件事：few-shot 取样是否把真正有信息量的失败案例送进去、记忆是否会把验证集指标回灌、以及同一上下文被重复采样了多少次。

第三件事最容易被低估。若 `a_t` 由同一个 `C_t` 以 `batch_size` 次并行采样得到，则上下文不变而试验次数线性增长；每一次采样都要进入多重检验的分母，却没有对应机制折减显著性。调研报告把这一点称作「重复采样把试验次数放大，却没有任何机制折减显著性」（§3.2.6），这正是 FactorMiner 早期样本外收益为负的成因之一。

下面给出带注释的闭环伪代码，对应 `core/miner/paradigms/llm_miner.py:109-193` 与 `core/miner/entities.py:90-116` 的真实结构。

```python
# 生成—执行—反馈闭环（无梯度；更新的是上下文，不是参数）
def llm_mining_loop(panel, returns, n_iterations, batch_size=5):
    S = build_system_prompt(panel)      # 注入面板真实字段与加密流语义
    state = MinerState()                # successful_reflections / failed_reflections

    for t in range(n_iterations):
        # 1. 构造上下文：系统提示 + 最近 5 成功 / 5 失败的 few-shot
        F = state.get_llm_context_prompt()
        prompt = S + "\n" + F
        prompt_sha256 = sha256(prompt.encode("utf-8")).hexdigest()

        # 2. 同一 prompt 采样 batch_size 次；注意这会同步放大试验分母
        responses = api.batch_generate([prompt] * batch_size)

        # 3. 代码抽取 + provenance 绑定（只存摘要，不存原文与密钥）
        candidates = []
        for resp in responses:
            code = re.sub(r"```python|```", "", resp).strip()
            candidates.append(FactorExpressionCode(
                code_str=code, sandbox=sandbox,
                provenance={"generator": miner_name, "model": model_name,
                            "prompt_sha256": prompt_sha256, "iteration": t}))

        # 4. 沙盒真实执行 + 指标计算；失败也产生可学习的错误类型
        feedback = evaluator.evaluate(candidates)

        # 5. 反思记忆：成功/失败分流，各裁剪到最近 100 条
        successful = []
        for expr in candidates:
            res = feedback.for_candidate(expr)
            if not res:
                continue
            if res.succeeded:
                state.successful_reflections.append(
                    {"code": expr.get_source(), "metrics": res.metrics})
                successful.append(expr)
            else:
                state.failed_reflections.append(
                    {"code": expr.get_source(),
                     "error_type": res.error_type, "error": res.error_message})
        state.successful_reflections = state.successful_reflections[-100:]
        state.failed_reflections    = state.failed_reflections[-100:]

        # 6. 记忆快照随候选落盘；population 只留本轮成功候选供 Director 入库
        snapshot = state.get_llm_context_prompt()
        for expr in candidates:
            expr.set_reflection_history(snapshot)
        state.population = successful
    return state.population
```

### 8.3 提示词工程与泄漏控制

few-shot 池的设计有两条经验值得说明。其一，**失败样本必须与成功样本同等保留**。报错类型（维度不符、索引不对齐、非法属性、缺 `factor` 赋值）是对语法约束最直接的教材；只留成功样本，模型会在同一堵墙上反复撞。FactorMiner 把两个池都裁到最近 100 条（`llm_miner.py:188-189`），组装提示时各取最后 5 条（`entities.py:109,112`），失败信息截断 500 字符（`:114`）——有界是为了防止提示词线性膨胀，取最近是为了让记忆跟上当前轮次的分布。其二，反思文本是训练产物，不是研究产物：`MyCustomLLM` 明确把反思历史与高分代码候选分开保存（`my_custom_llm.py:345-356`），前者进下一轮提示，后者才按 Top-K 写入 `state.population` 供入库。

泄漏控制要守三层，且三层的性质完全不同。

第一层是**模型背诵**。LLM 的训练语料覆盖了回测年份里已发表的 alpha 与行情复盘，直接问「给我一个 2021 年 CSI300 上有效的因子」，模型可能只是在复述记忆，而非从数据里发现结构。`LLM-Alpha-Mining-Framework` 用 `latest_visible_year` 限制提示词可见年份来防背诵（`evo/config.py:9,27-54`），并把三段窗口钉死为 fit 2000–2013 / validation 2014–2017 / holdout 2018–2025，配一句 「Nothing is tuned on the holdout, ever.」。它的 README 还主动承认 holdout 并不干净、LLM 训练数据覆盖 2018–2025、信号 IC 仅 0.0005–0.0101——这种自曝其短比任何漂亮数字都更可信。

第二层是**验证集指标回灌**。反思记忆若把验证集 IC 写进 archive 或送回 feedback，留出区间就会被搜索过程反复消费，等于用验证集做训练。`LLM-Alpha-Mining-Framework` 的做法是「validation IC 从不写入 archive entry 的 metrics、从不传给 feedback」，并且**用测试强制**这条纪律（`evo/runner.py:16-17`）——把纪律写成断言，比写进文档可靠得多。反例是 RD-Agent：`prompts.yaml:187-190` 鼓励「任何微小改进都替换最佳结果」，且 hypothesis 阶段能看到历史 test 指标（§3.1.5），存在间接信息泄漏。

第三层是**提示词里的事实边界**。幻觉出不存在的列是 LLM 因子最低级也最普遍的失败。FactorMiner 的 `initialize_search_space` 从面板读出真实列名写进 system prompt，并要求「只引用这些字段，绝不发明列」（`llm_miner.py:75-80`）；若面板里存在加密原生流，还会把 `CRYPTO_STREAM_SPECS[s]["rationale"]` 拼进去，例如资金费率是「多空拥挤度仪表，极值均值回复」、基差是「carry 与情绪，高基差先于去杠杆」（`:81-93`），并提示优先使用 z-score、delta、rank、比率这类平稳变换而非原始水平。这解决的是「别写 `df['vwap']`」这一类问题，属于数据感知，不是假设生成——两者之间还隔着结构化规格、独立 critic 和执行内自纠错三道工程。

顺带值得记下一种省算力的纪律：`LLM-Alpha-Mining-Framework` 的文本 gate 在碰 DataFrame 之前就拒掉约 90% 候选（`fitness.py:3-6`）。能靠静态规则判死的候选，就不该消耗一次沙盒进程和一次面板求值。

### 8.4 安全沙盒：静态策略与进程隔离

这里必须先纠正一个常见误解：LLM 沙盒做的是 **Python 源码的 AST 白名单**，不是「因子 AST 白名单」。GP 生成的表达式树是受限 DSL，节点只有算子与终端，天生无法表达 `import`、`open`、`__class__` 或无限循环；LLM 输出的是任意 Python 文本，攻击面是整个语言。因此只能在 `ast.parse` 之后按节点类型逐项放行，任何未被显式列举的语法都默认拒绝。`core/evaluation/code_sandbox.py` 的 `FactorCodePolicy`（`:154-243`）就是这个 fail-closed 的 `ast.NodeVisitor`。

四层边界依次是：

**语法层**。`_ALLOWED_NODE_TYPES`（`:109-151`）放行 Module、Assign、Name、Constant、Subscript、Slice、Tuple、List、Dict、Call、Attribute、BinOp、UnaryOp、BoolOp、Compare、IfExp 及各类运算符节点；`import`、循环、函数/类定义、`with`、`lambda`、推导式、`await` 因不在白名单里，被 `generic_visit`（`:173-178`）直接抛 `SecurityError`。注意这里没有「黑名单」：`docs/architecture/v4_architecture_design.md:417` 明确写了字符串关键字黑名单不是安全边界，也不得重新引入。

**名字层**。`_SAFE_BUILTINS`（`:37-47`）只放行 9 个内置名——`abs`、`min`、`max`、`len`、`range`、`list`、`dict`、`float`、`int`；`_SAFE_ATTRIBUTES`（`:49-101`）放行 49 个 pandas / NumPy 方法，覆盖 `pct_change`、`rolling`、`shift`、`rank`、`ewm`、`corr`、`winsorize`，以及 `Series`、`DataFrame`、`array`、`exp`、`log1p`、`maximum`、`minimum`、`nan`、`sqrt` 等入口。`visit_Assign`（`:180-191`）禁止向 `df` / `np` / `pd` 及内置名赋值、禁止 `_` 前缀的私有或 dunder 变量名，并强制至少存在一次对 `factor` 的赋值；`visit_Attribute`（`:225-228`）拒绝 `_` 开头属性；`visit_Call`（`:230-242`）只允许已批准的内置与属性调用，并禁止动态或私有关键字参数。

**常量层**。`_MAX_NUMERIC_CONSTANT = 1_000_000`、`_MAX_POW_EXPONENT = 6`（`:106-107`）。这两条不是可选的加固，而是平台缺口的补偿：Windows 上没有 `resource` 模块，`RLIMIT_AS` / `RLIMIT_CPU` 会静默失效（`:103-105`、`:319-332`），沙盒只剩墙钟超时；此时 `x = list(range(10**9))` 是完全合法的语法，却能在超时触发前耗尽进程内存。`visit_Constant`（`:201-209`）与 `visit_BinOp`（`:211-223`）把数值常量绝对值和幂指数分别压在上限内。POSIX 上则由 `_apply_resource_limits` 补上 `RLIMIT_CPU`、`RLIMIT_AS`、`RLIMIT_NOFILE`（`:323-328`）。

**进程与输出层**。`RestrictedSandbox.execute_factor_code`（`:385-428`）用 `multiprocessing.get_context("spawn")` 起一个 `daemon=True` 的短生命周期子进程（`:391-397`），父进程以 `parent.poll(timeout_seconds)` 做墙钟超时，超时即 `terminate` / `kill`（`:401-409`）；worker 的 `__builtins__` 只由白名单重建（`:341-348`），编译后 `exec`，再交给 `validate_llm_factor_output`（`:258-316`）。后者是索引对齐校验：顺序模式要求返回 `pd.Series`，长度等于输入行数、`index` 与输入 DataFrame 完全相等且无重复（`code_sandbox.py:263-279`）；`cross_asset` 模式要求每个特征值都是 DataFrame 且彼此的 `index` / `columns` 完全一致，输出 `pd.DataFrame` 的 `index` 与 `columns` 必须与参考帧完全相等且无重复（`:281-315`）；最后统一校验数值 dtype、至少一个有限值、不含 `inf`（`:245-255`）。`FactorExpressionCode.compute`（`core/miner/expressions.py:117-123`）是 fail-closed 的最后一环：没有显式传入 sandbox 直接抛错，不存在退回裸 `exec()` 的兼容路径。

```python
# 沙盒执行主路径（对应 code_sandbox.py:382-428，带注释）
def execute_factor_code(code_str, data):
    # 1) 静态校验：AST 白名单 + 名字/属性白名单 + 常量与幂上限
    tree = FactorCodePolicy().validate(code_str)
    if not policy.factor_assigned:
        raise FactorOutputError("必须把结果赋给变量 factor")

    # 2) 进程隔离：spawn 出的 daemon 子进程，避免继承父进程状态
    ctx = multiprocessing.get_context("spawn")
    parent, child = ctx.Pipe(duplex=False)
    proc = ctx.Process(target=_sandbox_worker,
                       args=(child, code_str, data, limits), daemon=True)
    proc.start(); child.close()

    # 3) 墙钟兜底：POSIX 另有 RLIMIT_CPU/AS/NOFILE，Windows 只剩这一层
    if not parent.poll(limits.timeout_seconds):
        proc.terminate(); proc.join(1)
        if proc.is_alive(): proc.kill(); proc.join(1)
        raise SandboxTimeoutError("LLM 因子执行超出墙钟预算")
    result = parent.recv()

    # 4) 输出契约：类型、长度、index/columns、数值 dtype、有限值
    output = validate_llm_factor_output(result["output"], data)
    return output            # 只有走到这里，代码才算「真正执行成功」
```

| WorldQuant-LLM / alphaminingv2 | 生产者—消费者在线闭环（WQ Brain API + SQLite + cron），启发式调度与失败指纹黑名单；alphaminingv2 有相位状态机与工具 dispatch | 精英杂交、挽救池、`Sharpe<-0.8` 自动取反；alphaminingv2 的 `enable_critic` 默认 **False**（`agent/config.py:63`） | 筛选完全依赖平台返回的 **`Sharpe≥1.25 & fitness≥1.0`**（`run_alpha_miner.py:1132-1133`）；反复 sweep / rescue / 反向重测 | 工程运维闭环完整，**统计检验为零**，是 data snooping 温床；`data/` 为空，算子运行时从平台拉取 |
| AlphaMaster | REINFORCE + 自回归 Transformer 生成 8-token 公式；动作掩码保证语法合法 | 精英池与相关性软惩罚 | 验证集每步复用、无 gap / embargo、无逐折重拟合 | **AI 只解说**：`web/ai_analyze.py` 读快照出中文报告，`model_core/` 与 `train_file.py` 零 LLM 调用；四条闸门全缺 |
| FactorMiner LLM | 单一 system prompt 重复 `batch_size`（默认 5）次采样，输出纯 Python 代码 | 成功 / 失败反思各留 **100** 条、取最近 **5+5** 组 few-shot；AST 白名单 + spawn 沙盒；源码 MD5 硬去重 + 面值软去重 | 正式档案只持久化 Prompt 的 SHA-256 摘要，候选级 provenance 递归移除密钥；统计闸门在评估层而非 LLM 层 | **仅数据感知，不是 RD-Agent 闭环**：无假设层、无结构化规格、无 critic、无单轮自纠错；可复现性靠 Recorder 单独留痕 |

一句话读表：前六个环节（假设、实现、执行、批判、记忆、筛选）大家的差别主要在工程精度，第七环「统计闸门」才是分水岭；而「AI 解说」根本不在挖掘层内，不该与前六行并列比较。

### 8.6 FactorMiner 实现

**初始化**（`core/miner/paradigms/llm_miner.py:44-107`）。`initialize_search_space` 先按 `data_feeds.mining_mode == "cross_asset"` 切换输入契约（`:52-66`）：顺序模式下 `df` 是 `pd.DataFrame`，要求把对齐的 `pd.Series` 赋给 `factor`；`cross_asset` 模式下 `df` 是「特征名 → 对齐 DataFrame」的映射，要求赋 `pd.DataFrame`。system prompt 先写死角色与「只输出代码、不要 markdown」，再注入 `_available_fields()` 的真实列名（`:75-80`）与 `CRYPTO_STREAM_SPECS` 的 `rationale` 语义（`:81-93`）。沙盒按 `llm_sandbox` 构造 `RestrictedSandbox(timeout_seconds=5.0, cpu_seconds=3, memory_mb=1024)`（`:47-51`），`batch_size` 默认 **5**（`:107`）。该类从 `core/evaluation/evaluator.py:12-18` 导入沙盒，后者只是把 `code_sandbox.py` 的定义转出，真正的实现只有一份。

**生成**（`:109-151`）。`prompt = system_prompt + "\n" + state.get_llm_context_prompt()`（`:114`），`prompt_hash = sha256(prompt.encode("utf-8")).hexdigest()`（`:115`），随后 `prompts = [prompt] * batch_size`（`:118`）交给 `LLMAPIManager.batch_generate`（`:122`）。未配置 API 时降级为两条 mock 表达式 `factor = df['close'].pct_change(1)` 与 `factor = df['volume'] * df['close']`（`:126-129`）——这是可用性兜底，不是研究成果，实验模式可用 `require_live_api` / `allow_fallback=false` 把它关掉（`docs/guides/custom_llm_experiments.md:83-85`）。回答用 `re.sub(r'```python|```', '', resp).strip()` 清洗（`:136`），包装成 `FactorExpressionCode`，provenance 含 `generator`、`model`、`prompt_sha256`、`iteration`（`:142-147`）。

**更新**（`:158-193`）。`feedback.for_candidate(expr)` 把结果与候选严格绑定（`core/miner/entities.py:59-63`）；失败写 `failed_reflections` 的 `code / error_type / error` 并把 `evaluation_status="error"` 回填 provenance，成功写 `successful_reflections` 的 `code / metrics` 并回填 `evaluation_status="success"`（`:161-187`）；两个池各裁到最近 **100** 条（`:188-189`）；`reflection_snapshot = state.get_llm_context_prompt()` 经 `set_reflection_history` 绑到每个候选（`:190-192`）；最后 `state.population = successful`（`:193`）。注意这与 `MyCustomLLM` 不同：后者按 fitness 排序、跨轮保留 Top-K 档案（`my_custom_llm.py:348-356`），核心版只把本轮成功候选交给 Director。`MinerState` 在 `core/miner/entities.py:90-116`，两个池定义在 `:99-100`，few-shot 取 `[-5:]` 与 `[-5:]`（`:109,112`）。

**归档与脱敏**。`core/miner/director.py:322` 把 `cand.get_provenance()` 交给存储层；`core/storage/factor_storage.py:13-21` 定义 `_SENSITIVE_PROVENANCE_KEYS`（`api_key / apikey / authorization / credential / password / secret / token`），`:24-39` 的 `_sanitize_provenance` 对 dict / list / tuple **递归**剔除键名含这些标记的项，`:186` 在写入前调用，`:244` / `:262` 给出 NN 通道与弃用接口的同类处理。因此正式因子档案只持久化 Prompt 的 SHA-256 摘要（`README.md:414`），既不存原文也不存密钥。

**实验留痕**。`LLMExperimentRecorder` 位于 `user_workspace/experiment_tools/llm_recorder.py`，由 `my_custom_llm.py:48-53` 装配，保存完整 Prompt（`:124`）、模型原始回答（`:153`）、`prompt_sha256`、`output_sha256` 与 `deterministic_replay_equal`（`:191-192`），以及候选代码、执行结果与 Reflection 事件；目录 `user_workspace/experiments/` 默认被 Git 忽略。之所以必须单独留痕，是因为 **LLM 范式因外部 API 非确定**：`LLMAPIManager` 的采样 `temperature=0.7`（`core/miner/paradigms/llm_api_manager.py:85`），同一 prompt 每次回答都可能不同，只存摘要的正式档案无法复现生成过程。Recorder 只观察事件、不参与候选排名，也不改变因子值（`docs/guides/custom_llm_experiments.md:27`）；`require_live_api` 保证没有真实凭证就停机，`allow_fallback=false` 禁止用随机公式冒充模型候选。

**密钥与并发**。API 密钥通过 `llm_api_config.keys_env` 指定的环境变量注入（指南 `:35-42` 示例为 `["AI_API_KEY", "OPENAI_API_KEY"]`），`my_custom_llm.py:85-114` 解析环境变量、剔除占位符并自动补全 `/chat/completions`；`LLMAPIManager._redact_sensitive_text`（`llm_api_manager.py:57-79`）对日志里的 Bearer token 与 `sk-` 前缀做脱敏。`evaluation.max_workers` 默认是 8（`core/evaluation/evaluator.py:75`，取值 1–64），但 LLM 候选每个都要起一个短生命周期进程，README 给出的建议配置是 `{"evaluation": {"max_workers": 2}}`（`README.md:430-441`）。

### 8.7 工程陷阱与本章小结

**工程陷阱**

1. **训练数据覆盖回测年份造成的隐性泄漏。** 这是 LLM 范式独有的、无法靠代码沙盒拦住的泄漏：模型可能只是在复述语料里已发表的 alpha。用 `latest_visible_year` 钉死提示词可见年份、把最终留出区间设为模型知识截止之后、并在报告里主动声明这一限制，三者缺一不可。
2. **同 prompt 重复采样等于把试验分母快速烧光。** `batch_size` 次采样共享同一上下文，既不构成独立发现，又线性抬高多重检验的 `num_trials`。要么让每轮的 few-shot 与温度真实变化以产生多样性，要么把重复次数如实计入试验分母并交给闸门折减；绝不能把 5 条近似重复代码当作 5 个独立因子。
3. **幻觉代码必须真实执行，而非「看起来合理」。** 一段读起来像动量因子的代码，可能索引错位、全为 NaN 或引用了不存在的列。只有 `validate_llm_factor_output` 的索引对齐与有限值校验全部通过，才算候选；`docs/guides/custom_llm_experiments.md:126` 那句「代码通过沙盒不代表研究解释正确」还应再往前推一步：解释正确也不代表可以交易。
4. **反思记忆把验证集指标回灌提示词。** 若 validation 或 holdout 的 IC 被写进 archive 或 feedback，留出区间就从「一次性裁决」退化成「反复消费的训练集」。正确做法是把这条纪律写成测试断言，而不是写进规范文档。
5. **API 密钥不得写进 JSON / 源码 / 提交记录。** 配置只放 `llm_api_config.keys_env` 的环境变量名；`_sanitize_provenance` 虽会递归剔除凭证键，但它是最后一道兜底，不能当作允许明文落盘的理由。实验目录保存完整 Prompt 与原始回答，即使被 Git 忽略也应按研究数据限制访问与备份范围。
6. **沙盒并发与内存。** 每个候选一个 `spawn` 短生命周期进程，Windows 上还没有 `RLIMIT_AS` 兜底，并发数直接乘以单进程内存占用。`evaluation.max_workers` 建议压到 2，并保留 `llm_sandbox` 的 5 秒墙钟 / 3 秒 CPU / 1024 MB 限制；否则高并发下先崩的不是因子逻辑，而是机器本身。

**本章小结**

1. LLM 在因子研究中有候选代码生成器、假设与实验设计者、结果解说员三种位置；「用了 LLM」不等于「LLM 挖因子」，AlphaMaster 的 `web/ai_analyze.py` 属于解说层，其 `model_core/` 与训练脚本零 LLM 调用。
2. 生成—执行—反馈闭环的更新对象是上下文 `C_t` 而非参数 `θ`，`∂L/∂θ = 0`；闭环质量由记忆裁剪、few-shot 取样与试验次数纪律决定，没有优化器提供收敛保证。
3. 泄漏控制的三层分别是模型背诵（`latest_visible_year` 与知识截止后的留出）、验证集指标回灌（用测试强制的隔离）、提示词事实边界（只注入面板真实字段与语义）；FactorMiner 只做了第三层，因此是「仅数据感知，不是 RD-Agent 闭环」。
4. LLM 沙盒必须针对 **Python 源码**做 AST 白名单，而不是复用因子表达式 DSL 的约束；在 Windows 缺少 POSIX 资源限制时，常量规模上限与墙钟超时是补上平台缺口的**补偿性控制**，不是可选加固。
5. FactorMiner 的 LLM 是「数据感知 + 反思记忆 + 强沙盒」的轻量闭环，尚缺假设层、结构化规格、独立 critic 与单轮自纠错；正式档案只存 Prompt 的 SHA-256 摘要，可复现性由 `LLMExperimentRecorder` 在 user_workspace 中单独保存完整生成证据来补齐。
