## 第 16 章 可复现性与端到端实验流水线

> 本章回答：可复现凭什么不只是同种子跑出相同数字？因子的身份该由哪几个字段钉死，四个哈希各防哪种漂移？为何首版 manifest 字段齐全却判为不可复现？八阶段流水线如何用净化、禁运期与逐折重拟合做实时间隔离？成本与数据口径怎样统一到一处？八阶段全绿的正式 run，为什么仍不等于挖到赚钱的因子？

### 16.1 什么叫"可复现"：过程可复现与结果有效

把"可复现"理解成"同一个种子能跑出相同数字"，是最常见也最廉价的误读。种子只固定随机数发生器，固定不了配置改没改、算子集增删没增删、数据文件补没补过尾、以及当时累计做了多少次试验。一个成熟的因子平台真正要能回答的是一整串问题（`docs/research/platform_maturity_gap.md:74`）：**这个因子是哪次运行、哪份配置、哪版算子集、哪版数据、哪个种子产生的，当时的试验分母是多少，之后又在哪些窗口被验证过？** 前半句关乎身份，后半句关乎证据链；只答得出前半句，仍然无法判断因子是被独立复验过，还是同一段数据被反复偷看。

因此可复现是一个合取条件，而不是一个布尔开关：

```
Reproducible(process) = ∧( run_id, config_hash, git_sha,
                           operator_set_hash, data_snapshot_hash,
                           seed, num_trials, 已验证窗口集 )

reproducible ⇔ mismatches = ∅
```

符号解释：`∧` 表示每一项都"可回答且可核对"；`run_id` 是运行唯一标识，`config_hash / git_sha / operator_set_hash / data_snapshot_hash` 分别钉死配置、代码、可执行算子集与数据快照，`seed` 固定随机性，`num_trials` 是当时的累计试验分母，`已验证窗口集` 记录此后哪些时间/标的窗口被揭示过；`mismatches` 是 `verify_manifest()` 把存储值与当前值逐字段比对后不相等的字段集合。注意最后两行的关系：**`reproducible` 判定的是"当前环境能否重放那次运行"，不是"那次运行的结论是否成立"**。

这两件事必须分开，否则会犯一个代价极高的错误：把流水线绿灯读成因子有效。用判据写清楚：

```
process_green  ⇏  OOS_net > 0
```

`process_green` 只说明配置、代码、数据、种子、成本、时间隔离全部对得上，过程可审计；`OOS_net > 0` 是经济结论，取决于有没有真信号、成本是否吃光边际、以及验证窗口是否干净。前者可以靠工程补齐，后者不能。`docs/research/platform_maturity_gap.md` 把成熟度拆成能力覆盖 A、纪律可信 D、结果产出 R、运营可复现 O 四维，并写明 **R 是乘数**：R = 1 时，A、D、O 再高也只等于"一套很严谨、暂时还没挖到东西的研究工具"。本章讲的所有机制，都属于把 O 从 4 提到 6 的那类工作——它们能防返工，不能提高产出。这个边界要在读任何一张绿色状态表之前先立住。

### 16.2 Manifest 身份六字段、四个哈希与一个真实缺陷

`core/experiment/manifest.py` 是可复现基座，模块 docstring（`:1-10`）把职责说得很克制：回答"哪份配置、哪版代码、哪版算子集、哪版数据、哪个种子产生了这个因子，以及评估它时已经试过多少次"。`build_manifest()`（`:139-184`）产出的身份由六个字段承载，`manifest_summary()`（`:187-198`）再把它们压缩后盖进每个因子的 `data_lineage`：

| 字段 | 含义 | 生成方式（精确到实现） |
|---|---|---|
| `run_id` | 运行唯一标识 | `new_run_id()`（`:134-136`）：UTC 时间戳 + `os.urandom(3)` |
| `config_hash` | 配置快照 | `hash_json()`（`:30-36`）：canonical JSON（`sort_keys=True`、`separators=(",", ":")`、`ensure_ascii=False`）的 sha256 |
| `git_sha` | 代码版本 | `git rev-parse HEAD` 取前 12 位，无 `.git` 时返回 `unknown`（`:39-51`） |
| `operator_set_hash` | 可执行算子集版本 | `sha256("\|".join(sorted(BUILTIN_OPERATORS ∪ OperatorRegistry._registry)))[:12]`（`:54-68`） |
| `data_snapshot_hash` | 数据快照 | 每个可读取的 feather 文件读头 64KB + 尾 64KB 参与 sha256，再用文件清单的哈希汇总（`:88-115`） |
| `seed` | 全局随机种子 | `seed_everything()`（`:118-131`）同时设 `random.seed` 与 `np.random.seed`；NN 范式自己持有 `default_rng(seed)` |

四个哈希各防一种漂移，这一点比"用了哈希"本身更重要。`config_hash` 防的是"参数悄悄改了但沿用旧结论"；`git_sha` 防的是"代码换了实现、旧因子值却照用"；`operator_set_hash` 防的是**算子集版本漂移**——若某个算子的实现被替换，历史因子面值必须重算，而不能被缓存复用；`data_snapshot_hash` 防的是"数据补了尾、或某个文件被覆盖，却没人发现"。数据指纹只读头尾各 64KB 而不是整文件，是在大面板的 I/O 成本与敏感性之间取的折中：文件被截断、被追加、被整体替换，头尾摘要都会变。

`verify_manifest()`（`:201-221`）的判定式就是上一节那一行代码：

```
checks    = {config_hash, git_sha, operator_set_hash, data_snapshot_hash}  当前重算值
observed  = manifest 里的存储值
mismatches = {k: {stored, current} | observed[k] 存在且 observed[k] != checks[k]}
return {"reproducible": not mismatches, "mismatches": mismatches, "current": checks}
```

它同时服务两个入口：`--resume` 与全库重审。只要算子集或数据快照变了，缓存的因子值就不得复用——不是给个警告，而是把 `reproducible` 判成 `False`。

下面是一个 **结构片段**，取值仅示意字段类型（`run_id` 用正式 run 的真实标识，其余哈希值以占位表示，避免把示意值误读成实测摘要）：

```json
{
  "schema_version": 1,
  "run_id": "run_20261114T104814Z_b9eb49",
  "created_at": "<UTC 秒级时间戳>",
  "config_hash": "<canonical JSON 的 sha256>",
  "config_path": "user_workspace/configs/configExperiment.json",
  "git_sha": "<git rev-parse HEAD 前 12 位>",
  "operator_set_hash": "<sha256(sorted 算子名)[:12]>",
  "data_snapshot": {
    "hash": "<文件清单 sha256[:16]>",
    "n_files": "<本次可读 feather 数>",
    "files": ["<path / size / digest>", "..."]
  },
  "seed": "<int 或 null>",
  "seed_applied": true,
  "paradigm": "GP",
  "timeframe": "1d",
  "windows": { "mine": ["<...>"], "test": ["<...>"] },
  "n_trials_at_start": 0,
  "environment": { "python": "<...>", "platform": "<...>" },
  "notes": { "llm_nondeterministic": false }
}
```

**一个真实缺陷证明这些字段不是装饰。** 首版端到端流水线跑出来的是 `reproducible = False`，而 manifest 六个字段一个不少。原因藏在阶段顺序里：`load_user_modules()` 是在**挖掘阶段**才注册用户算子的（`core/experiment/pipeline.py:60` 的 `_stage_mining` 里有这次调用），但 manifest 在更早的**预注册阶段**就把算子集指纹化了。于是预注册时 `operator_set_hash` 只覆盖内置算子，挖掘阶段用户算子一注册，当前值就与存储值不一致，`verify_manifest()` 如实报 mismatch。修复是把用户模块加载**提前到 manifest 生成之前**（`docs/research/platform_maturity_gap.md:18`、`TODO.md` P6「测试中修掉的真实缺陷」都记录了这一条）。

这个缺陷的价值在于它的因果链非常干净：字段设计对了、哈希算法对了、比对逻辑也对了，唯独**观测时机**错了，整个身份就失效。它同时说明 `operator_set_hash` 不是给报告凑列的元数据——它真的会抓出"算子集在两次指纹化之间变了"这件事。若当初为了图省事把它换成"记录一下配置里写了哪些算子名"，这个缺陷就会被静默吞掉，而旧因子值与新算子实现混用的后果要等到 OOS 归因时才暴露。

### 16.3 八阶段流水线与阶段级 resume

`core/experiment/pipeline.py:1-44` 把此前散落在脚本与库函数里的能力编排成一条一键流水线，docstring 里的顺序即产品定义：

```
预注册(created) → 数据质量 → 挖掘 → 晋升闸门 → walk-forward
→ 组合检查 → 验证段 OOS 重算 → 回测 → 报告/归档
```

`STAGES`（`:35-44`）是 8 个执行阶段：`data_checked / mining / gated / validated / combined / oos_prepared / backtested / completed`；归档时另有 `created` 预注册节点，所以 `status.json` 共记录 **9 个状态**（`docs/README.md:79-81`）。每个阶段的状态与 artifact 由 `core/experiment/registry.py` 登记到 `user_workspace/runs/<run_id>/`，`index.jsonl` 追加索引；失败会把阶段名写进 `status.json`，**不吞异常**。

带注释的伪代码如下（对应 `pipeline.py` 的真实编排骨架）：

```python
# 八阶段流水线骨架（伪代码，带注释）
def run_experiment(config, run_id, resume=False):
    run_dir = f"user_workspace/runs/{run_id}"
    # 阶段 0 预注册(created)：身份必须先于任何数据读取被钉死
    load_user_modules(config['user_dir'])        # 必须提前！否则 operator_set_hash mismatch
    manifest = build_manifest(config, run_id=run_id,
                              n_trials_at_start=budget.cumulative())
    costs.check_identity(config)                # gate_cost_rate 恒等式校验
    holdout_guard(mode='strict', purpose='final')  # 一次性留出，先登记再跑，崩了也算烧掉

    for stage in STAGES:                        # 8 个阶段，逐一落 status.json
        if resume and stage_already_done(run_dir, stage):
            continue                           # --resume 仅按阶段跳步
        result = dispatch(stage, config, run_dir)
        registry.record(run_dir, stage, result)  # append-only，失败也落盘（带 stage 名）
        if not result.ok:
            write_status(run_dir, stage, 'failed', reason=result.reason)
            raise PipelineError(stage)

    # 归档：配置 / manifest / manifest_final / state / metrics /
    #       walk_forward / report.md / status + index.jsonl
    final = verify_manifest(manifest, config)  # {reproducible, mismatches, current}
    archive(run_dir, manifest_final=final, report=render_report())
    return final

# 三处隔离（pipeline.py 的设计约束，见 :6-15）
# ① 候选写入 <run_dir>/factor_db，绝不污染共享 factor_db
# ② 验证段因子值重算到 <run_dir>/factor_db_oos
# ③ 回测方向用 orientation_db_root 指向样本内库，杜绝符号泄漏
```

三处隔离是流水线能被称为"实验"而不是"又跑了一次挖掘"的关键。候选隔离写入 `<run_dir>/factor_db`，让一次运行的产物不会混进全局因子库；验证段 OOS 重算到 `factor_db_oos`，保证回测读取的是在留出窗口上重新计算过的面值；`orientation_db_root` 从样本内库学方向，符号在训练期冻结，验证段的信息无法回流。第 17 章讲过的 `resolve_signal_weights` 与 `load_factor_signals` 正在这里被复用——权重贯通不是回测页的补丁，而是流水线的一个阶段。

`--resume` 的边界必须讲清：它**只按阶段跳步，不恢复 epoch 级 GP 种群**（`docs/README.md:74,97`）。也就是说，长跑若在挖掘阶段第 3 代中断，`--resume` 会重跑整个挖掘阶段，而不是从第 3 代续上。这是 `platform_maturity_gap.md` 明确列出的"仍未解决"项之一，属于 S4/S5 的 epoch 级断点续训。诚实地标注这个边界，比让使用者以为断点续训已经完整更负责任。同理，LLM 范式因为依赖外部 API，`notes.llm_nondeterministic` 会被置为 `true`——即便 `reproducible = True`，也不能宣称那次运行可字节级重放。

### 16.4 时间隔离：净化、禁运期与逐折重拟合

时间隔离是八阶段里最容易被"看起来做了"蒙混过去的一环。`core/experiment/walk_forward.py:1-14` 的 docstring 直接点了两个失败模式：一是完全没有净化(purge)与禁运期(embargo)，训练/验证边界上算出来的标签会漏进下一段；二是 AlphaMaster 式"walk-forward"——**同一公式在全样本上算完面值，再把评分切片成折**，全程没有重拟合，于是每一折都在用"已经看过它验证数据"的权重打分。

FactorMiner 的 `build_folds()`（`:35-76`）用 expanding-window 5 折（`DEFAULT_WF_CFG.n_folds = 5`，`:24-32`），三行公式把边界钉死：

```
train_end       = val_start − horizon_bars − 1
embargoed_start = val_start + embargo_bars
gap_bars        = embargoed_start − train_end − 1
```

符号解释：`val_start` 是第 k 折验证段的名义起点；`horizon_bars` 是标签的持有期，`train_end` 再往回退 1，保证训练段最后一个标签 `t + horizon` 不会落进验证窗口，这就是净化；`embargo_bars` 把验证段起点继续往后推，给序列相关性留出衰减距离，这就是禁运期。代入 `horizon_bars = 1`、`embargo_bars = 5`（`DEFAULT_WF_CFG`）：`gap_bars = (val_start+5) − (val_start−2) − 1 = 6`，与正式 run `gap 全为 6 bars` 的实测一致（`:74`）。

更关键的是**每折独立重拟合**。`walk_forward_validate()`（`:196-251`）在每一折里只做三件事：

```
(μₖ, σₖ) = fit(f[:, train_sliceₖ, :])                 # 标准化统计量只在 TRAIN 上拟合
wₖ       = solve(XₖᵀXₖ + αI, Xₖᵀyₖ)                  # 岭权重只在该折 TRAIN 上求解
ICₖ      = RankIC( Σᵢ wₖᵢ · zᵢ , r )  on val_sliceₖ   # 验证段只用于打分
判据： |{ w₁, …, w₅ }| > 1  ⇒  weights_differ_across_folds = True
```

符号解释：`f` 是对齐后的因子面板张量，`r` 是未来收益，`Xₖ` 由第 k 折训练段标准化后的因子展平而成，`α = ridge_alpha = 5.0`，`zᵢ` 是用 `(μₖ, σₖ)` 变换后的第 i 个因子，`ICₖ` 是该折验证段的截面 RankIC。最后一行是**反自欺判据**：如果五折解出的权重向量完全相同，说明所谓"逐折重拟合"根本没发生，很可能又退回"全样本算完再切片"。`weights_differ_across_folds = True`（`:248-250`）是显式验证，不是日志里一句自述。

`_standardise()`（`:131-139`）把 mean/std 的拟合范围严格限制在 `train` 切片上，再把同一变换应用到 `other`（验证）切片；`_fit_ridge()`（`:142-155`）在样本不足或矩阵奇异时退化等权或 `np.linalg.lstsq`。配套的 `cost_rate = 0.0018`、`quantile = 0.20` 让 `_net_return()`（`:172-193`）在每折都按同一口径扣换手成本，避免"IC 为正但净收益为负"被折均值掩盖。

对照之下，AlphaMaster 的做法是把同一公式在全样本上算完再切片评分，`docs/README.md:88` 明确写"避开 AlphaMaster『全样本算完再切片』的假 walk-forward"。两者的差别不在折数，而在**权重是否在每一折重新看过且只看过训练段**。有折无重拟合，形式上像 walk-forward，实质上仍是把验证数据用进了权重。

### 16.5 成本与数据口径统一，以及运维闭环

成本口径不统一，是"闸门放行、回测亏钱"最直接的来源。`core/experiment/costs.py:1-10` 把问题讲得很清楚：晋升闸门按每单位多空换手收 `gate_cost_rate`，事件驱动回测按每边收 commission + slippage，这两个数字描述的是同一笔经济成本，必须相等：

```
gate_cost_rate = 2 × (commission_rate + slippage_rate)
0.0018        = 2 × (0.0004 + 0.0005)
consistent    ⇔ |implied − gate| < 1e-6
```

`DEFAULTS`（`:17-21`）给出 18bp 往返 = 两边各 4bp 手续费 + 5bp 滑点；`resolve_cost_params()`（`:24-45`）从 `fitness.gate_cost_rate`、`backtest.commission_rate`、`backtest.slippage_rate` 三处读值，算出 `implied` 与 `delta`，把 `consistent` 写进 run 报告。正式 run 的 `consistent = True`。这解决的是 `platform_maturity_gap.md:172` 记下的旧状态：fitness 用 18bp 常数、回测用另一个常数 funding，**两处口径不同源**，因子可能过了闸门却在回测里亏钱。

真实资金费也接进了同一口径。`core/backtest/backtest_engine.py:346-380` 的 `load_funding_series()` 把 8h 结算流按交易 bar 频率 `resample(freq).sum(min_count=1)` 聚合——`min_count=1` 保证"该 bar 内一次结算都没有"时留 `NaN`，而不是被静默当成 0 费率；`build_funding()`（`:383-414`）对缺失 bar `fillna(常数)` 回落，并在 `attrs` 里写 `funding_source`（如 `crypto_streams (20 assets)` 或 `constant`），`run_backtest()` 的 summary 再记 `funding_source`（`:603`）。正式 run 真实 funding 命中 20 标的，机制验证 run 命中 6 标的。

数据面前置校验同样不可省。`core/data_feed/panel_validator.py` 在首次 `get_data()` 时校验重复时间戳、索引乱序、K 线缺口、覆盖率、全空/常数标的与极端收益；`data_quality.strict = true` 时 critical 问题直接拒跑（`README.md:257-260`）。正是这条能挡住当初混进 holdout 的 **31 根重复 K 线**（`TODO.md` §3b）。增量补数 `scripts/update_data.py` 只补尾部、幂等空跑、裁掉晚于截止日的未收盘 K 线（一次 2025-01 的补数实测**裁掉 652 根**越界数据）、失败按指数退避重试 3 次并写 JSON 报告（`README.md:292`）。

运维闭环决定"没人看着时能不能跑对"。新鲜度视图按周期拆分滞后（`1d` 允许 2 天、日内 1 天），一根停更的 15m 文件不会被读成"整个库坏了"，反过来也不会被日线的正常掩盖；读不出时间列或文件名不规范的文件单独报 `summary.unreadable`，不再静默跳过——这条通道曾让一个 30 MB 无时间轴的 1m 文件完全隐形（`README.md:273-275`）。预注册窗口进度由 `GET /api/data/freshness` 与 `GET /api/gates/holdout` 返回，界面显示 accumulated/remaining/coverage/ETA 进度条，而不是靠记忆决定哪段数据还没烧（`TODO.md` §3c）。任务持久化到 `.workbuddy/tasks.json`：取消在 epoch 边界抛 `MiningCancelled` 优雅退出并落库为 `cancelled`，服务重启后原 `running` 任务降级为 `interrupted`，不再出现幽灵任务；`--allow-holdout-reuse` 逃生口会被强制写进 `reports/holdout_overrides.jsonl`（`TODO.md:12,53`）。CI（Python 3.12 pytest + Node 20 构建）与 Docker 四个状态目录 bind mount 则保证换台机器起得来、研究产物不丢。

### 16.6 正式 run、竞品对照与诚实边界

正式 run `user_workspace/runs/run_20261114T104814Z_b9eb49/` 是这套机制第一次完整受检（`docs/README.md` §5、`TODO.md` P6）：**8 stages completed，641 bars / 0 warning**；**4 候选 / 4 落库 / 0 promoted**，`empirical_p` **4/4 已计算**（其中 3 个被 `empirical_null_pass` 拦下）；`val_read_count = 87`；**5 折逐折重拟合**（gap 全为 6 bars，1 个组合因子）；**4 份 OOS 快照**；真实 funding 命中 20 标的；`manifest_final.json` 的 **`reproducibility = True`、`mismatches = {}`**；两次相同种子运行的回测收益只差浮点末位。全量回归 `python -m pytest -q` → **431 passed / 1 skipped / 56 subtests**（唯一 skip 是 `test_factor_analytics.py` 缺 `httpx` 的既有环境问题）。

但同一份报告里还有一行：**验证段回测 -4.43% / Sharpe -0.37**。把它和上面所有绿灯放在一起读，才是这一章真正要交付的判断：

> **绿色流水线只证明"过程可复现、可审计"，不等于挖到了赚钱的因子。**

一次性 strict holdout 在这次 run 里根本没被触碰，`0 promoted` 说明闸门没有放行任何候选；正向证据要由滚动预注册窗口（锚点 2026-11-14、30 根/窗 + 5 根 embargo，首个窗口 ETA 2026-12-13）或标的维度留出提供。把八阶段全绿读成"系统有效"，等于把 `process_green` 误当成 `OOS_net > 0`——这正是 16.1 立下的边界。

下表把可复现与工程纪律放到竞品口径下对照，可以看到各家补齐的是不同层：

| 系统 | run 身份 / 版本戳 | 时间隔离 | 成本口径 | 断点续训 | 已知缺口 |
|---|---|---|---|---|---|
| qlib / RD-Agent | 无统一 run manifest；RD-Agent 有 SOTA 库 0.99 相关去重 | 无 purge/embargo 记录 | 反馈含 `with_cost`，无统一恒等式 | 无 | RD-Agent `M4 = 0`，无多重检验校正 |
| AlphaMaster | `vocab.py:48-58` 词表 `sha256(算子名)[:12]`；训练包导入校验 `vocab_version` | **假 walk-forward**：全样本算完再切片评分 | 三端共用信号函数，`drop_forming=True` | 每 20 步原子写 ckpt（模型+优化器+两个池+best_snapshot+history） | 验证集反复复用，因子退化为 beta；zip-slip / CORS 全开等安全问题 |
| trade-learn | MLflow 实验追踪 | 下游快回测，不负责挖掘期隔离 | Rust 引擎独立计费 | 非训练态 | 0.3.x、68 处 `NotImplementedError`，`CausalSelector` 不证明样本外有效 |
| FactorMiner（本流水线） | manifest 六字段 + 四个哈希 | expanding 5 折 + purge 1 + embargo 5，`weights_differ_across_folds=True` | `gate_cost_rate = 2×(commission+slippage)` 同源 | **仅阶段级**，不恢复 epoch 级 GP 种群 | R = 1，尚无正向 OOS 证据 |

读表要抓住两点。第一，**工程成熟度不等于方法论成熟度**：AlphaMaster 的断点续训与训练包导入是最完整的产品化层，却因为验证集反复复用退化成 91.8% 做多的 beta；RD-Agent 工程生态顶级但 `M4 = 0`；qlib 是数据/执行事实标准却不含挖掘器。第二，**FactorMiner 补的正是"过程可审计"这一层**：manifest、八阶段、purge/embargo、成本恒等式、真实 funding、逐折重拟合，都属于把 O 从 4 提到 6 的接线工作；它们能让结论跨机器成立、让失败可定位，但**不能把 R 从 1 变成 2**。`docs/research/platform_maturity_gap.md:12` 的四维评分补记里，结果产出一项自始至终是 1，原因就在这里。

### 16.7 工程陷阱与本章小结

#### 工程陷阱

1. **账本被 gitignore**。`.fdr_ledger*.jsonl` 与 `.experiment_trace.jsonl` 曾被 `.gitignore` 忽略，换台机器 clone 后 `num_trials` 归零，DSR 分母被系统性低估，闸门看起来比实际宽松。修复方向是"可提交的单调快照 + 追加日志双文件"（`core/experiment/budget.py` 的 `.hypothesis_budget.json`），让累计假设数跨机器只增不减。
2. **roll-forward 有折无重拟合**。折数画得再漂亮，若五折共用一个权重向量、或标准化统计量在全样本上拟合，就是 AlphaMaster 式假 walk-forward。必须用 `weights_differ_across_folds` 这类显式判据验证，而不是相信日志里那句"已做逐折重拟合"。
3. **成本两处口径不同源**。fitness 用 18bp 常数、回测用另一套常数 funding，会出现"过了闸门却在回测里亏钱"。`consistent = |delta| < 1e-6` 要作为 run 的硬校验写进报告，而不是事后对账时才发现。
4. **小标的池 0 交易静默空回测**。回测默认 5 多 / 5 空、`min_assets = 10`，6 币预留池下每次调仓都被拒，产出"0 交易、0% 收益、成功"的假绿。`adapt_book_to_universe()` 按实际资产数自适应：6 币 → 2 多 2 空、20 币仍 5/5，并用真实价格文件的回归测试锁定"必须真的成交"。
5. **LLM 范式外部 API 非确定**。`notes.llm_nondeterministic` 会被置真；即便 `reproducible = True`，也不能宣称那次运行可字节级重放。把 LLM run 与 GP/RL run 用同一套"同种子必然相同"的预期去审计，是口径错配。
6. **把阶段绿灯读成因子有效**。八阶段全通过、`mismatches = {}`、两次同种子只差浮点末位，全部只证明过程可复现。正式 run 同时给出 `-4.43% / Sharpe -0.37` 与 `0 promoted`，就是要让这个边界无法被含糊过去。

#### 本章小结

1. 可复现不是"同种子跑出相同数字"，而是能回答"哪次运行、哪份配置、哪版算子集、哪版数据、哪个种子、当时试验分母多少、之后在哪些窗口被验证过"；`reproducible ⇔ mismatches = ∅` 判定的是**过程能否重放**，不是结论是否成立。
2. Manifest 六字段由四个哈希钉死：canonical JSON sha256、`git rev-parse HEAD` 前 12 位、`sha256(sorted 算子名)[:12]`、数据文件头尾各 64KB 的快照摘要；`seed_everything` 同时固定 `random` 与 `np.random`，NN 用 `default_rng`。
3. 首版 `reproducible = False` 的根因是 `load_user_modules()` 在挖掘阶段才注册用户算子、而算子集在预注册阶段就已指纹化；修复是把用户模块加载提前——**算子集版本戳不是装饰，它会真的抓出版本漂移**。
4. 八阶段流水线（`STAGES` 8 个 + `created` 共 9 个 status）用 `<run_dir>/factor_db`、`factor_db_oos`、`orientation_db_root` 三处隔离杜绝污染与符号泄漏；`--resume` 仅阶段级，不恢复 epoch 级 GP 种群。
5. 时间隔离的实质是三行公式 `train_end = val_start − horizon_bars − 1`、`embargoed_start = val_start + embargo_bars`、`gap = 6 bars`，加上每折只在 TRAIN 拟合 mean/std 与岭权重、并用 `weights_differ_across_folds = True` 自证"有折且真重拟合"；成本由 `gate_cost_rate = 2×(0.0004+0.0005) = 0.0018` 单点统一。
6. 正式 run `run_20261114T104814Z_b9eb49` 八阶段全绿、641 bars / 0 warning、`reproducibility = True`、`mismatches = {}`、431 passed / 1 skipped / 56 subtests，但验证段回测 **-4.43% / Sharpe -0.37、0 promoted**：**绿色流水线只证明过程可复现可审计，不等于挖到赚钱的因子**，R 仍是乘数。
